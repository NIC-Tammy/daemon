# Ellucian daemon

`daemon168/` is the OpenShift `dmi-listener` BuildConfig's Git context. Its
`Dockerfile` starts the daemon on port 9000, as configured by
`daemon168/dmi.ini`. The daemon handles SA Valet requests to install and start
separate DMI listeners; a running daemon does not establish that a listener has
been registered or started.

## Unix listener startup

The bundled `daemon168/ext/daemon.jar` has separate Unix install and start
handlers. Installation registers a listener in `/etc/datateltab` as
`priority:name:listener-directory:jre-directory:Y|N`. Starting it looks up
that entry and executes `/opt/ellucian/daemon/scripts/datatelmgr start name`.
`datatelmgr` checks the entry, the JRE directory, `dmi.ini`, and
`dmilistener.jar` before launching Java. The bundled startup scripts must be
executable (mode `100755` in Git); the Dockerfile also restores execute bits
if a build input loses them.

The Dockerfile creates `/opt/ellucian/tmp` as a writable scratch directory
for the OpenShift UID (root group). Its contents are transient and should
not be committed or treated as a listener installation backup. If the
running pod predates this image change, the directory can be created
without restarting SQL Server:

```bat
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- mkdir -p /opt/ellucian/tmp
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- test -w /opt/ellucian/tmp
echo %ERRORLEVEL%
```

This only establishes a writable path **in the listener container**.
After DORE connectivity succeeded, SQL Server `BULK INSERT` returned
error 4860 for a file under `/opt/ellucian/tmp`; the SQL container had
no such directory. Containers in a pod share a network, not their root
filesystems. The source-controlled ODS StatefulSet must mount the
same scratch volume (for example, `emptyDir`) at `/opt/ellucian/tmp`
in **both** containers, with permissions that let the listener write
and SQL Server read. The image directory will be hidden by that mount.
The failed file was already absent from listener tmp when inspected
after the attempt, so the shared mount fixes visibility, not proof
that transfer created the file or kept it long enough for SQL to read.
Do not roll out a StatefulSet change until the existing ephemeral
listener installation can be restored or recreated and the SQL
Server restart is scheduled.

`startdmi` and `stopdmi` are generated in the installed listener directory
*when `datatelmgr` starts it*; they are not files to copy from the image.
The installed listener's `dmi.ini` is generated by `InitRegistry`, not the
daemon template at `daemon168/dmi.ini`. `InitRegistry` only sets `ListenerName`
when passed `-L` and encrypts `RegistryPassword` when passed `-w`. Blank fields
alone do not prove registration failed: the Unix start command also supplies
the listener name as `-n` and can pass authentication arguments at startup.
Do not copy an encrypted password from a Windows listener into Linux without
confirming it can be decrypted with that listener's keystore.

On the inspected `tammy2` pod, registration **did** complete:
`/etc/datateltab` contains
`2:test_ods_sql07:/opt/ellucian/test/ods_sql07:/etc/alternatives/jre:N`
and is writable by the pod's UID. The listener is marked `N` (not
auto-started). Before the executable-bit fix, `scripts/datatelmgr` had
mode `0664` and `test -x` failed for that UID. Correct the image's script
permissions before interpreting blank `dmi.ini` fields as an install
failure.

After that fix, the installed listener started Java but did not open its
configured data port (7277). Its `nohup.out` reported registry read errors
for `DMIERRORS`: a list of separate numeric IDs appeared as one record ID,
with UTF-8 replacement characters between the IDs. The bundled
`UniObjectsAccount.readList()` splits selected IDs at the field-mark
character (code point 254), so the malformed list could not be processed
as separate records. This does **not** establish where the characters
were replaced in the installed UniObjects client.

In a controlled, listener-only test, adding `-Dfile.encoding=ISO-8859-1`
to the **installed listener's** SA Valet JVM Arguments allowed a Java
listener process to bind port 7277, and its latest log had no
`Unable to start server` entries. A later scoped `SPT_BUILDINGS` refresh
completed, but that does not establish that the charset is safe for all
data. Keep the setting limited to `test_ods_sql07`; do not change the
daemon's Dockerfile, base daemon JVM, SQL Server, or global locale to
reproduce it. Record the approved listener-specific setting in the SA
Valet installation procedure (or a reviewed non-secret template), and
verify non-ASCII data handling before making it permanent.

SA Valet initially advertised the RDAS listener at
`10.1.34.24:7277`, but the live `dmi-listener` LoadBalancer exposed
only port 9000. DORE Check Connectivity returned `DMI_OPEN` error 16
("Unable to connect to the listener"). Applying a Service-only change
from the ODS repository exposed 7277; a Windows TCP probe then
succeeded and SA Valet reported the listener running. DOTA's separate
**Database Host Name** is the SQL Server target on port 1433
(observed as `10.1.34.21:1433`); do not point it to the RDAS Service.
Restrict the non-TLS listener port to required clients and publish
the applied Service manifest to source control.

A separate RDAS-only LoadBalancer was allocated `10.1.34.25:7277`
but was not used for DORE and was subsequently removed. It was not
established that SA Valet could advertise a distinct RDAS data address
independently of daemon management on port 9000. Do not repoint the SA
Valet host or DOTA SQL host to that unused address, and do not keep a
declarative Service that would recreate it.

After network reachability was restored, DORE's file-transfer check
reported `User error-10015` while SQL Server recorded no new login
failure. The listener logged `Unable to authenticate a client login
from (100.64.0.9,100.64.0.9)`. The bundled
`DMIServerSocketAuthenticator` emits that message when no enabled
authentication-server record exactly matches the connecting client's
host address or host name; it is **not** by itself evidence that the
SQL password is wrong. At the time of this failure, the shared Service
used `externalTrafficPolicy: Cluster`, which can replace the original
client IP before the listener sees it. Compare the observed address
with the approved `AUTHSERVRS` entries in SA Valet and establish the
actual client source path before changing authentication or Service
policy. Do not blanket-allowlist a shared cluster address or disable
authentication. A reversible Service-only trial of
`externalTrafficPolicy: Local` on the **existing** LoadBalancer kept
both ports reachable on `10.1.34.24`, and DORE Check Connectivity then
passed. This strongly implicates source-address translation, but the
accepted client identity needs independent verification. A subsequent
scoped `SPT_BUILDINGS` refresh completed; the Full DORE run did not.
A `Local` policy affects both port 7277 and daemon
management on port 9000; before committing it as permanent
configuration, validate this cluster's load-balancer behavior during
pod/node rescheduling and retain a tested rollback. Publish the
successful Service policy in the ODS repository rather than relying
on the live-only change.

After securely backing up the installed listener and importing it to
the dedicated PVC, the StatefulSet was rolled out with a shared
`emptyDir` at `/opt/ellucian/tmp` in both containers. The restored
listener started, DORE Check Connectivity passed, and a scoped
`SPT_BUILDINGS` refresh completed successfully through SQL bulk load.
This verifies the transfer path for that transform, not a full ODS
refresh. Keep the protected backup until retention and recovery
requirements are met.

## ODS_ADDRESS bulk-load diagnosis

The later Full DORE run ended with 86 of 436 target transforms in error
status. A controlled `ODS_ADDRESS` retry showed successful UniData
extraction and listener file transfer, followed by SQL Server error
4863 during `BULK INSERT` at row 3, column 11 (`ZIP`). At that retry,
`ZIP` was `varchar(10)` in both tammy2 and production; the import's
`MAXERRORS=1000` accounts for the 1,001-error summary. This is a
different failure from the earlier missing-file error 4860.

For one authorized diagnostic, a protected extract was retained
temporarily and inspected **only for aggregate field counts and byte
lengths**. All 17,764 lines ended in CRLF and had 11 fields; 15,330
final `ZIP` fields exceeded 10 bytes only when their terminal CR was
counted, and none exceeded 10 bytes without it. A separate, synthetic
three-row CRLF file with a 10-byte final field failed on this SQL Server
build with the DORE-generated `ROWTERMINATOR = '\n'` syntax (SQL 7330);
the same file loaded all three rows with `ROWTERMINATOR = '0x0d0a'`,
without a CR in `ZIP`. This strongly implicates the generated import
terminator for `ODS_ADDRESS`; it does not establish that the other 85
transforms share this cause or that a user-editable setting exists.

As an A/B test, the user changed DOTA's `ODS_ADDRESS.ZIP` width from 10
to 20 in tammy2. A later scoped run with the temporary 2025+ filter
completed and loaded 17,764 rows, but read-only aggregate checks found
that **all 17,764 ZIP values end in `CHAR(13)`**, 15,330 exceed the
original 10-byte limit, and the maximum stored length is 11 bytes.
The live test target is now `varchar(20)`, unlike production's
`varchar(10)`. Widening masks the truncation and stores the CR; it is
neither an import fix nor a full-history validation. Obtain an
import-side terminator correction, reconcile the target width with the
approved specification, then reload and validate the data before
using it for reports.

Microsoft's [bulk terminator documentation](https://learn.microsoft.com/en-us/sql/relational-databases/import-export/specify-field-and-row-terminators-sql-server?view=sql-server-ver16)
says `BULK INSERT ROWTERMINATOR = '\n'` expects CRLF, unlike the
observed synthetic test with DORE's other bulk-load options on tammy2
SQL Server 2022/Linux. A custom vendor patch is not the only possible
path. On a disposable SQL Server 2022 CU27 GDR1 instance
(`16.0.4305.5`), the same three-row synthetic file and DORE-style
import options again returned SQL 7330; explicit
`ROWTERMINATOR = '0x0d0a'` loaded all three rows with no CR in ZIP.
This newer build did **not** resolve the reproduced case; no live SQL
image or PVC was changed for the comparison. The probe Pod, dedicated
Secret, and local password file were removed, and the live SQL pod
remained healthy. Give Microsoft the
sanitized reproduction and evaluate a reviewed import stage with
explicit terminator control or another SQL target that passes the
same test. A replacement must have a supported way to obtain inputs
and preserve retries and data protection; do not race DORE's
temporary-file cleanup with a watcher. Protect SQL backups and
define rollback before any live SQL change.

Import success does not by itself establish clean values: a read-only
check of a separate loaded `ODS_ACAD_PROGRAMS` table found that the
last text column ends in `CHAR(13)` in **all 445 rows**. This is a
specific data-quality finding, not proof about every other table.
Validate affected last-column values with aggregate-only checks and
seek a supported import correction before relying on reporting data;
do not bulk-update SQL values or infer a repair from status alone.

After the Full run, the installed listener's saved heap setting was
raised from `-Xms512M;-Xmx512m` to `-Xms1024M;-Xmx1024m` and the
listener was restarted. A scoped `SPT_STUDENT_ACAD_CRED` retry then
advanced past its earlier abort and wrote rows, but still ended with
1,001 row errors. The combined heap increase and restart helped the
earlier symptom; their individual contributions and the row-error
cause have not been isolated. Listener logs had no explicit OOM/GC
marker. Preserve the required listener-only `ISO-8859-1` setting;
neither heap change nor restart corrects the `ODS_ADDRESS` import
terminator or contaminated ZIP values.

The debug flag was cleared and the exact retained diagnostic and
synthetic files were removed after the test. DOTP exposed only target
drive and temporary-path settings, not a row-terminator setting. Until
a supported import path is tested, do not treat a completed retry,
the widened `ZIP`, trimmed protected records, increased `MAXERRORS`,
or listener heap as a substitute for clean data. Keep raw `.dor` logs,
extracts, record keys, and address values out of Git and support
notes; share only sanitized diagnostics through an approved protected
channel.

## Inspect an SA Valet start failure in `tammy2`

From Windows Command Prompt, first confirm the BuildConfig strategy is
`Docker`, its Git source is this repository, and the pod is `sqlserver-0`.
These commands run Linux checks *inside* the daemon container, not the SQL
Server container. For each `test`, exit code 0 means the path is usable;
run `echo %ERRORLEVEL%` immediately after it to see the result:

```bat
oc -n tammy2 get bc dmi-listener -o jsonpath={.spec.strategy.type}
oc -n tammy2 get bc dmi-listener -o jsonpath={.spec.source.git.uri}
oc -n tammy2 get bc dmi-listener -o jsonpath={.spec.source.contextDir}
oc -n tammy2 get pods -o custom-columns=NAME:.metadata.name,CONTAINERS:.spec.containers[*].name
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- id
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- ls -ld /etc/datateltab /opt/ellucian/test /opt/ellucian/test/ods_sql07 /opt/ellucian/daemon/scripts/datatelmgr
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- test -x /opt/ellucian/daemon/scripts/datatelmgr
echo %ERRORLEVEL%
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- test -x /bin/ksh
echo %ERRORLEVEL%
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- test -w /etc/datateltab
echo %ERRORLEVEL%
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- test -w /opt/ellucian/test
echo %ERRORLEVEL%
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- grep -F :test_ods_sql07: /etc/datateltab
```

The record must point to `/opt/ellucian/test/ods_sql07` and a JRE directory
containing `bin/java` (or `java`). If the record is absent after an install,
investigate the install response and whether the random OpenShift UID can
write `/etc/datateltab`; the Unix install handler writes this file directly.
If the record is present but `datatelmgr` is not executable, rebuild and
deploy the corrected image before retrying the start.

Check file presence, size, and permissions without dumping generated
configuration or secrets. The `sed` command prints only whether each field
is set, not its value:

```bat
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- ls -l /opt/ellucian/test/ods_sql07/dmi.ini /opt/ellucian/test/ods_sql07/dmi.keystore /opt/ellucian/test/ods_sql07/registry.xml /opt/ellucian/test/ods_sql07/pr.xml /opt/ellucian/test/ods_sql07/startdmi /opt/ellucian/test/ods_sql07/stopdmi
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- sed -nE "s/^(ListenerName|RegistryPassword|RegistryUser)=(.+)$/\1=<set>/p; s/^(ListenerName|RegistryPassword|RegistryUser)=$/\1=<blank>/p" /opt/ellucian/test/ods_sql07/dmi.ini
oc -n tammy2 logs sqlserver-0 -c dmi-listener --since=30m
```

Check the restored listener-specific charset setting without printing
`JVMArguments`: Java Properties may write `=` as `\=`, which
`datatelmgr` unescapes when it launches Java. An exact grep for
`file.encoding=ISO-8859-1` can falsely report that the setting is
missing:

```bat
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- sh -ec "grep '^JVMArguments=' /opt/ellucian/test/ods_sql07/dmi.ini | grep -Fq 'ISO-8859-1'; echo listener-jvm-setting-present"
```

For the installed listener's data port, the following *read-only* check
looks for hexadecimal port `1C6D` (7277) in the pod network namespace;
TCP state `0A` means listening. It does not prove that SA Valet or ODS
can complete a transaction:

```bat
oc -n tammy2 exec sqlserver-0 -c dmi-listener -- sh -c "grep -i ':1C6D ' /proc/net/tcp /proc/net/tcp6 || true"
```

Review logs privately before sharing: the vendor start handler and
`datatelmgr` can log command arguments, including credentials. Look for an
install/registration error, `Permission denied` when executing `datatelmgr`,
or a listener launch error in `dmi.log`/`nohup.out`. Do not run
`datatelmgr start` as a diagnostic: it changes state and may expose
credentials in the generated `startdmi`.

## Reproducible deployment boundary

The `tammy2` deployment manifests are in
[`north-idaho-college/ods/yaml`](https://github.com/north-idaho-college/ods/tree/main/yaml),
not this repository. That repository's `dmilistener_buildconfig.yaml` builds
from **this** repository's `daemon168/` directory. Both repositories are
required to reproduce the deployment; do not edit a different copy of the
daemon files and assume the BuildConfig will pick it up. Review source
manifests against the live StatefulSet before claiming the sidecar and
storage are reproducible; do not commit an unreviewed cluster export.

- Keep the BuildConfig, ImageStream, StatefulSet, services, storage claims,
  non-secret registry coordinates, ports, paths, and startup settings in
  source-controlled YAML/ConfigMaps.
- Keep registry and SQL credentials, listener keystores, and other key
  material in OpenShift Secrets supplied by an approved secret-management
  process, not in Git or a ConfigMap.
- Treat the installed listener's `dmi.ini`, `registry.xml`, `pr.xml`,
  `dmi.keystore`, `startdmi`, and `stopdmi` as runtime artifacts. Review
  generated XML and `.ini` contents for credentials before deciding which
  non-secret fields to template. The packaged `daemon168/dmi.ini` and
  `daemon168/dmi.keystore` are distinct from the installed listener's files.
- `/etc/datateltab` must remain writable by the container's OpenShift UID
  during SA Valet installation. A ConfigMap mounted directly over it is
  read-only. The vendor install handler overwrites this file in place, so
  a pre-created writable file on the listener PVC can be mounted with
  `subPath`. Do not pre-register the listener on a fresh install: the
  install handler rejects duplicate names.

Before migration, `/etc/datateltab` and
`/opt/ellucian/test/ods_sql07` were on the ephemeral container
filesystem. A protected backup was imported to the separate 5Gi
`netapp-nfs-rwx` listener PVC and verified before the pod was
replaced. The StatefulSet now mounts that PVC for installed listener
state and uses a separate pod-lifetime `emptyDir` for file transfer;
restarting the pod will still restart SQL Server and require the
listener to be started in SA Valet unless auto-start is configured.
Source-controlled manifests alone do **not** recreate a fresh
listener installation: SA Valet registration, generated files,
keystores, and approved Secrets also require a documented bootstrap
and recovery procedure. Do not commit the protected backup.
